Concept

OKLCH의 L, C, H

L은 밝기, C는 무채색 축에서 떨어진 정도, H는 hue 각도다. C 0.15만으로 하나의 색을 지정할 수 없는 이유는 L과 H가 아직 정해지지 않았기 때문이다.

주의 OKLCH 좌표가 sRGB 화면에서 모두 표현 가능한 것은 아니다. 출력 전에 gamut mapping이 일어날 수 있다.

Input interpretation · heuristic

achromatic · subdued · chromatic은 무엇인가?

입력 hex를 OKLCH로 측정한 뒤 chroma C로 설명용 class를 붙인다. 이는 색 이름이나 품질 등급이 아니다. hue가 거의 의미 없는 입력을 안전하게 다루고 diagnostic cohort를 구분하기 위한 현재 runtime 경계다.

achromaticC < .015

hue를 생성에 사용하지 않고 neutral family를 만든다.

subdued.015 ≤ C < .06

낮은 chroma 입력. 현재 생성 경로는 chromatic과 같고 주로 설명·분석 class다.

chromaticC ≥ .06

hue와 상대 chroma를 Primary 후보 생성에 사용한다.

한계 .015와 .06은 지각 실험으로 보정된 보편적 무채색·유채색 경계가 아니다.

Color conversion · technical strategy

sRGB 밖의 OKLCH 색을 어떻게 화면 안으로 가져오는가?

현재 방식: L·H 고정, C 최대 보존

OKLCH 좌표를 sRGB로 변환했을 때 R·G·B 중 하나라도 0…1 밖이면 화면이 그대로 표현할 수 없다. 현재 엔진은 lightness L과 hue H를 고정하고, sRGB 안에 들어올 때까지 chroma C만 낮춘다.

  1. low = 0, high = requested C
  2. mid = (low + high) / 2로 후보 C를 만든다.
  3. sRGB 안이면 low = mid, 밖이면 high = mid.
  4. 24회 반복 후 gamut 안의 가장 큰 C를 사용한다.
  5. 8-bit #RRGGBB로 반올림해 출력한다.
requested = OKLCH(L, C, H)↓binary-search C only↓mapped = OKLCH(L, Cmax, H)↓8-bit sRGB hex
requestedL .72 · C .40 · H 35°raw RGB 1.348 / −2.017 / −1.429 · sRGB 밖

왜 이 방법이며, 다른 선택은 무엇인가?

현재 방식

결정적이고 설명하기 쉽다. mode를 정하는 L과 색 정체성인 H를 요청 좌표에서 움직이지 않는다.

RGB clipping

매우 빠르지만 hue와 lightness가 크게 바뀌거나 서로 다른 입력이 같은 원색으로 붕괴할 수 있다.

Perceptual / local-MINDE

지각 차이를 기준으로 경계를 찾는다. 더 자연스러울 수 있지만 L·C·H 중 무엇이 변하는지와 임계값 정책이 추가된다.

Cusp·P3·joint mapping

hue별 gamut 경계, Display-P3, L 조정을 활용하면 chroma를 더 보존할 수 있지만 출력 환경과 contrast 결과가 달라진다.

한계 현재 방법은 지각적으로 가장 가까운 색이나 가장 쨍한 안전색을 보장하지 않는다. sRGB만 목표로 하며, 최종 hex 반올림 후 다시 측정한 L·C·H에는 미세한 차이가 생길 수 있다. 따라서 이것은 표준 정답이 아니라 현재 엔진의 technical 변환 전략이다.

후보 범위와 통과 경계는 다르다

후보 범위·반경·step은 어떤 색을 만들어 볼지 정한다. Constraint threshold는 만들어진 후보 중 무엇을 허용할지 정한다. Objective target은 통과 후보의 순서만 정한다. 숫자가 비슷해 보여도 같은 역할이 아니다.

Constraint · product-policy

Light L ≥ 0.96 · Dark L ≤ 0.185

왜 0.04가 아닌가?

0.96과 0.185는 Background 후보가 mode의 끝 영역에 있는지 검사하는 절대 L 경계다. 반면 ±0.04는 recipe 목표 주변에서 후보를 만들어보는 탐색 반경이다.

서로 다른 질문을 답하므로 같은 숫자일 이유가 없다. 현재 Light recipe는 0.995, Dark recipe는 0.145다.

Dark recipe .145Dark max .185Light min .96Light recipe .995

왜 규칙이 필요한가? Light 바탕이 너무 어둡거나 Dark 바탕이 너무 밝아 mode 구조가 뒤집히는 것을 막는다.

왜 정확히 이 값인가? Dark .185는 recipe .145에 일반 Foundation 후보 반경 .04를 더한 탐색 상한이다. 외부 표준이나 지각 실험으로 .96/.185가 입증되었다는 뜻은 아니다.

값을 바꾸면? 더 많은 Background 후보가 허용되거나 탈락한다. hierarchy·text·후속 역할 전체가 달라질 수 있다.

Authority product-policy. 목적은 명시됐지만 정확한 경계는 잠정적이다.

Concept · text contrast measurement

APCA와 Lc는 무엇인가?

APCA는 Accessible Perceptual Contrast Algorithm의 약자다. text와 배경의 밝기 관계를 Lightness contrast, 즉 Lc로 표현한다. |Lc|가 클수록 이 계산 모델에서 명암 대비가 강하다.

Lc 0에 가까움Aa읽기 어려움 |Lc|가 큼Aa명암 대비가 강함
어두운 text / 밝은 바탕 밝은 text / 어두운 바탕

+ / − 부호는 이 두 polarity를 구분한다. 이 엔진은 후보 진단 순위에서는 방향이 아니라 대비 크기인 |Lc|를 사용한다.

  • 퍼센트가 아니다Lc 75는 “75% 대비”라는 뜻이 아니다.
  • WCAG 4.5:1과 다르다계산 모델과 숫자 눈금이 달라 직접 변환해서 읽을 수 없다.
  • 75와 60은 표준값이 아니다현재 text 역할과 typography를 위해 정한 provisional heuristic이다.
  • 두 배경 중 불리한 값을 쓴다한 배경에서만 읽히는 후보가 통과하지 않도록 더 작은 |Lc|를 선택한다.

이 프로젝트에서의 사용 먼저 WCAG 4.5:1을 통과한 후보만 남긴다. 그 뒤 가장 약한 APCA 진단 점수가 큰 후보를 우선한다. Lc 75/60은 legacy-provisional 진단 목표이며 후보를 탈락시키는 권위가 아니다.

Concept · color-distance measurement

이 프로젝트의 ΔE는 어떻게 계산하는가?

OKLCH 두 색을 Oklab 좌표로 펼친 뒤, 두 점 사이의 직선거리를 구한다.

Δ는 “두 값의 차이”, E는 색 차이를 뜻한다. 여기서 사용하는 값은 CIEDE2000이 아니라 Oklab 공간의 Euclidean distance다. 밝기 L과 두 색 방향 축 a·b가 함께 달라진 만큼을 한 거리로 합친다.

OKLCH의 C와 H는 원형 좌표라 그대로 빼지 않는다. 먼저 같은 색을 직교 좌표 a와 b로 바꾼다.

a = C × cos(H × π / 180) b = C × sin(H × π / 180) ΔE = √((L₂−L₁)² + (a₂−a₁)² + (b₂−b₁)²)
  1. 1 · 측정두 hex를 실제 출력 sRGB에서 OKLCH로 측정한다.
  2. 2 · 좌표 변환각 색의 C·H를 a·b로 펼친다.
  3. 3 · 축별 차이ΔL, Δa, Δb를 계산한다.
  4. 4 · 거리세 차이의 제곱을 더하고 제곱근을 취한다.

같은 ΔE를 만드는 색은 하나가 아니다. 서로 다른 방향의 수많은 좌표가 같은 거리에 놓일 수 있다.

해석 한계 Oklab은 지각적 균일성을 목표로 만든 색 공간이지만 이 거리만으로 두 색이 의미상 구분되는지, 어느 색이 더 좋은지, 모든 화면에서 사용자가 차이를 인식하는지를 증명하지 않는다. 이 프로젝트의 .035/.05/.075/.08 기준은 외부 ΔE 표준 등급이 아니라 각 규칙에 붙인 heuristic 또는 provisional 정책값이다.

숫자보다 먼저: 왜 다른 색이어야 하는가?

Primary는 화면의 일반적인 대표 행동이고, Destructive는 삭제·제거처럼 되돌리기 어렵거나 위험한 행동이다. 두 역할이 나란히 놓였을 때 거의 같은 색이면, 사용자는 label과 위치만으로 둘을 구별해야 한다. 이 시스템은 역할의 차이가 색에서도 사라지지 않도록 Destructive 후보를 고를 때 이미 선택된 Primary와의 거리를 검사한다.

현재 적용 범위: semantic token의 역할 정체성과 실제로 두 filled 버튼이 동시에 보이는지는 다른 문제다. Accepted component hierarchy는 함께 있을 때 Destructive를 outline으로 낮추고, destructive confirmation에서는 Primary를 두지 않는다. 그럼에도 context-free palette는 ΔE .08을 selected-result review heuristic으로 유지한다. Policy v16은 이 값에 미달한 후보도 완전한 family와 label contract을 만족하면 생성할 수 있다. 대신 수치, threshold, false verdict를 숨기지 않고 review evidence와 semantic relation에 남긴다.

ΔE는 두 색의 Oklab 좌표가 얼마나 떨어져 있는지 나타내는 색 거리다. 0이면 같은 색이고, 값이 커질수록 수치상 더 멀다. 여기서는 역할별 색이 이미 선택된 색과 너무 가까운 후보를 선택된 결과의 관계를 표시하는 데 사용한다. 좌표 변환부터 실제 계산 예시까지 보기 →

두 최종 sRGB 색의 Oklab 거리가 현재 최소값을 통과했다.

위험 행동색이 브랜드 action색과 너무 가까운 후보를 제외한다.

Candidate step과 tolerance

0.0025, 0.005, 0.01 step은 후보 탐색 해상도와 비용을 정한다. 0.002, 0.001, 0.0005 tolerance는 gamut mapping과 부동소수점 경계 흔들림을 처리한다. 둘 다 사람이 느끼는 최소 차이로 해석하면 안 된다.
